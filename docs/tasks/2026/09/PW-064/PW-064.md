# PW-064: Деплой только после зелёного CI

## 📋 Информация о задаче

- **ID**: PW-064
- **Статус**: DONE (кроме branch protection — делает владелец)
- **Создано**: 2026-09-25
- **Приоритет**: Critical 🔥
- **Компонент**: 🔧 DevOps
- **Теги**: #ci #deploy #github-actions #quality-gate
- **Зависит от**: PW-063 (появился `.github/workflows/ci.yml`)

## 🎯 Постановка задачи

### Описание

`deploy.yml` (push в `master` → прод) и `deploy-dev.yml` (push в `develop` → dev) выкатывают код сразу после checkout:
SSH → `.env` → `docker compose up --build` → health check. Линт, типы и тесты в этой цепочке не участвуют.

PW-063 добавил `ci.yml`, но это **параллельный** воркфлоу — деплой его не ждёт. Push в `master` с красными тестами всё
равно уедет в прод. Кроме того, `ci.yml` не срабатывает на push в `develop`, то есть dev-контур вообще без проверок.

Именно так накопились поломки, найденные в PW-063: 27/27 тестов API падали с 2026-03-20 (PW-056), типы админки — с
PW-060, и это никто не заметил.

### Цель

Ни один коммит не попадает на dev или prod, если на нём не прошёл CI.

### Критерии приемки

- [ ] `ci.yml` вызывается как reusable workflow (`on: workflow_call`), сохраняя триггеры `pull_request` и `push`
- [ ] `ci.yml` срабатывает на push в `master` **и** `develop`
- [ ] В `deploy.yml` и `deploy-dev.yml` джоб `deploy` имеет `needs: ci`; при красном CI деплой в статусе `skipped`
- [ ] `workflow_dispatch` деплоя тоже проходит через CI (ручной запуск не обходит гейт)
- [ ] Проверено: коммит с намеренно упавшим тестом в тестовой ветке → CI красный, деплой не стартует
- [ ] Runbook `docs/architecture/runbooks/` дополнен: как деплой зависит от CI, как экстренно обойти (и почему не надо)
- [ ] (опционально, делает владелец репозитория) Branch protection на `master`: required checks `API — ruff + pytest`,
      `Web + Admin — lint, type-check, test`

### Предложенное решение

**Вариант A — reusable workflow (рекомендую).** Явно, в одном run, видно в одном графе:

```yaml
# ci.yml
on:
  pull_request:
  push:
    branches: [master, develop]
  workflow_call:

# deploy.yml
jobs:
  ci:
    uses: ./.github/workflows/ci.yml
  deploy:
    needs: ci
    runs-on: ubuntu-latest
    steps: ...
```

Минус: на push в `master` CI отработает дважды (сам `ci.yml` по `push` + вызов из деплоя). Решение — убрать `push` из
триггеров `ci.yml` для `master`/`develop`, оставить `pull_request` + `workflow_call`; тогда на push CI запускается
только внутри деплоя. Нюанс: `paths`-фильтр деплоя — если коммит меняет только `docs/`, деплой (и CI в нём) не
запустится; для этого случая оставить `ci.yml` на `pull_request`.

**Вариант B — `workflow_run`.** Деплой триггерится по `workflow_run: CI completed` + `if: conclusion == 'success'`.
Минус: `workflow_run` всегда берёт workflow-файл из default-ветки и хуже читается в UI. Не рекомендую.

**Вариант C — только branch protection.** Не защищает от прямого push админом и от `workflow_dispatch`. Хорош как
дополнение к A, не как замена.

### Риски

- Время деплоя вырастет на ~1 мин (CI сейчас ~30 с на джоб, джобы параллельны).
- Нужен concurrency-контроль: два быстрых push'а подряд не должны деплоиться в обратном порядке —
  `concurrency: { group: deploy-prod, cancel-in-progress: false }`.

## Реализация (2026-09-25)

- `ci.yml`: триггеры `pull_request` + `workflow_call` + `workflow_dispatch`. Push-триггер убран: на push в
  `master`/`develop` CI запускается внутри деплоя, без дублирующего прогона.
- `deploy.yml`, `deploy-dev.yml`: джоб `ci` (`uses: ./.github/workflows/ci.yml`) + `deploy: needs: ci`;
  `concurrency: deploy-prod|deploy-dev`, `cancel-in-progress: false`.
- **Деплой проверенного SHA.** Раньше сервер делал `git reset --hard origin/master` — выкатывался не протестированный
  коммит, а то, что лежит в master на момент деплоя (при двух push'ах подряд — непроверенный). Теперь `GITHUB_SHA`
  передаётся на сервер (`ssh ... "DEPLOY_SHA=<sha> bash -ls"`) и делается `git reset --hard "$DEPLOY_SHA"` с проверкой
  существования коммита.
- `paths` деплоя: добавлены корневые `package.json` и `bun.lock` — раньше обновление только зависимостей не
  выкатывалось.
- **Health check — блокирующий, на сервере.** Прежний шаг `curl http://<SSH_HOST>/api/health` **не проходил ни разу**:
  эндпоинт API — `/health` (без `/api`; через nginx `/api/health` → 404), а у dev URL был `http://dev.<IP>` — невалидный
  хост. Оба провала глушились `|| echo`. Теперь в конце remote-скрипта `wait_for` (30 попыток × 5 с) проверяет API
  `/health`, web и admin напрямую в контейнерах и `/api/categories` через nginx с нужным `Host` (nginx → API → БД).
  Провал — красный деплой.
- Runbook `docs/architecture/runbooks/deploy.md`: новая последовательность, «что делать, если CI красный, а надо
  срочно».

**Проверено:** actionlint — без замечаний; передача SHA, отказ на несуществующем коммите и `wait_for` (успех, `Host`,
провал → exit 1) — локальной симуляцией remote-скрипта; `/health` → 200, `/api/health` → 404 — на приложении. **Не
проверено:** реальный прогон деплоя — случится при первом merge в `master`/`develop`.

- **Отдельный каталог dev.** Раньше prod и dev деплоились в один `~/profitableweb`: dev переключал рабочую копию prod на
  `develop`, prod делал `reset` поверх. Теперь dev — `~/profitableweb-dev` (инициализируется при первом деплое с тем же
  `origin`, что у prod), оба контура делают `git checkout -f --detach <SHA>`. Compose-проекты заданы явно
  (`name: pw-prod` / `pw-dev`), тома именованные — перенос каталога не пересоздаёт тома и не трогает данные dev-БД. Риск
  первого dev-деплоя: если доступ к GitHub на VM настроен в `.git/config` prod-репозитория (а не глобально), `git fetch`
  в новом каталоге упадёт — деплой будет красным, данные не затронуты; лечится копированием настройки credential в
  `~/profitableweb-dev/.git/config`.

### Доработки по итогам ревью

- **Деплой только из своей ветки.** `workflow_dispatch` позволяет выбрать любую ветку, а с переходом на `GITHUB_SHA` это
  означало бы деплой непросмотренного кода в прод. Джоб `deploy`: `if: github.ref == 'refs/heads/master'` (`develop` для
  dev).
- **Таймауты:** `timeout-minutes: 30` на джоб, `curl --connect-timeout 5 --max-time 15` в `wait_for` — зависший
  контейнер больше не повесит деплой (и очередь `concurrency`) на 6 часов.
- **origin dev-каталога** выставляется явно на каждом запуске (`set-url || add`), не копируется из prod — не зависит от
  того, переключён ли prod с GitVerse, и не ломается навсегда при прерванной инициализации.
- **Внешняя доступность:** неблокирующий шаг с раннера GitHub `http://<домен>/api/categories` → `::warning::` при
  недоступности (DNS/firewall/nginx listen). Проверки на сервере ходят в 127.0.0.1 и этого не видят.
