### 🔥 Обнаружено: запланированные статьи никогда не публикуются

`schedule_article()` (`services/articles/admin.py:301`) и MCP-инструмент `schedule_article` ставят `status = SCHEDULED`
и `published_at` в будущем. MCP-ресурс даже описывает статус как «опубликуется автоматически».

Но **механизма автопубликации нет**: ни планировщика, ни фоновой задачи, а публичные запросы
(`services/articles/queries.py`) фильтруют строго `status == PUBLISHED`. Запланированная статья навсегда остаётся
невидимой для читателей, sitemap и RSS.

Календарь без работающего планирования — бессмысленный, поэтому автопубликация входит в эту задачу первой.

### Цель

1. Статьи в статусе `scheduled` публикуются в назначенное время без участия человека.
2. Календарь админки показывает реальные опубликованные и запланированные статьи и позволяет планировать.

### Часть 1: Автопубликация (API)

**Решение (рекомендую):** фоновая задача в `lifespan` FastAPI — раз в 60 с выполняет идемпотентный

```sql
UPDATE articles SET status = 'published'
WHERE status = 'scheduled' AND published_at <= now()
RETURNING id, slug
```

- Идемпотентно → безопасно при нескольких воркерах uvicorn (двойной запуск ничего не сломает).
- `published_at` уже хранит нужное время — отдельное поле не нужно.
- Каждая публикация пишет audit log (`actor = system`) и structlog-событие.
- После публикации web должен увидеть статью: проверить кеширование Next.js (ISR/`revalidate` у списков, sitemap, RSS) —
  при необходимости вызвать on-demand revalidation (`revalidatePath`) через защищённый web-роут.

**Альтернативы:** «ленивая» публикация на чтении (`PUBLISHED OR (SCHEDULED AND published_at <= now())` в каждом запросе)
— без фоновых процессов, но условие надо дублировать во всех запросах, sitemap, RSS и счётчиках категорий; легко забыть
одно место. Внешний cron (контейнер/systemd-таймер, дергающий `POST /api/admin/system/publish-due`) — надёжно, но ещё
одна движущаяся часть в деплое. Выбор фиксируем в ADR.

**Критерии:**

- [ ] ADR в `docs/architecture/decisions/` — выбранный механизм и почему
- [ ] Автопубликация работает; тест: статья с `published_at` в прошлом и статусом `scheduled` → после тика `published`
- [ ] Тик не падает при недоступной БД (лог + следующий тик)
- [ ] Статья появляется на сайте, в sitemap и RSS без ручных действий (проверить кеш)
- [ ] Отмена планирования: `scheduled → draft` из админки

### Часть 2: Календарь (API + Admin)

**API.** Эндпоинт `GET /api/admin/articles/calendar?from=&to=` — статьи со статусами `published` и `scheduled` с
`published_at` в диапазоне; ответ — `id, title, slug, status, published_at, primary_category{name,slug,color}`. Лёгкая
схема, без контента. Альтернатива — существующий `GET /api/admin/articles` с фильтрами `date_from/date_to` (решить при
реализации; отдельный эндпоинт проще и быстрее).

**Admin.**

- `useCalendarPosts(range)` в `hooks/api/`, маппинг в `ScheduledPost` (`calendar.types.ts`)
- `mockScheduledPosts` удалить; тип `ai-suggestion` пока не показывать (нет источника данных — это часть AI-центра)
- Клик по посту → редактор статьи (navigation-store)
- Drag & drop поста на другой день (если в видах календаря он есть; иначе — диалог «перенести») →
  `POST /articles/{id}/schedule`
- «Запланировать» из календаря: выбор черновика + дата/время → schedule
- Таймзона: `SystemSettings.timezone` уже есть (смещение вида `+03:00`, не IANA — переходы на летнее время не
  учитываются; для России допустимо) — отображать в ней, отправлять в UTC

**Критерии:**

- [ ] Календарь показывает реальные статьи за видимый период (месяц/неделя)
- [ ] Перенос даты работает, прошлое запрещено
- [ ] Время корректно с учётом `SystemSettings.timezone`
- [ ] `calendar.constants.ts` без моков, README раздела обновлён
- [ ] Тесты API для calendar-эндпоинта
