## 🎯 Постановка задачи

### Описание

На публичном сайте есть четыре элемента, которые читатель видит, но которые не работают или работают на заглушках. Хуже
отсутствующей функции — функция, которая делает вид, что работает.

| #   | Где                                                                 | Что сейчас                                                                                                                               |
| --- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| A   | `components/common/newsletter-form/NewsletterForm.tsx`              | `setTimeout(1500)` вместо запроса, затем тост **«Проверьте почту для подтверждения»** — письма нет, email никуда не сохраняется          |
| B   | `app-bar/app-bar-right/app-bar-actions/AppBarActions.tsx`           | кнопка поиска `HiSearch` без `onClick`                                                                                                   |
| C   | `components/common/feature-category-block/FeatureCategoryBlock.tsx` | `DEFAULT_CATEGORIES` (хардкод), `AppHomeHeroHeader` рендерит блок без пропсов → категории на главной не совпадают с реальными из админки |
| D   | `app/my-comments/page.tsx`                                          | `getUserComments('user-1')` — зашитый id; в проде страница показывает не комментарии текущего пользователя                               |

Задача делится на 4 независимые подзадачи; порядок — по соотношению «польза / трудоёмкость».

### PW-066-C: Категории на главной из API (S, ~1 ч)

**Решение.** `AppHomeHeroHeader` — серверный компонент: получить `getCategories()` из `lib/api-client.ts` (уже есть,
PW-054) и передать в `FeatureCategoryBlock`. `DEFAULT_CATEGORIES` удалить (не превращать в fallback — при недоступном
API лучше не показать блок, чем показать неправду).

**Критерии:**

- [ ] Блок показывает категории из БД, порядок — поле `order`, скрыта категория по умолчанию (`is_default`), если так
      решим
- [ ] Иконки/цвета: сейчас в моке у категорий есть визуальные атрибуты — сверить с полями `Category` в API (`color`?);
      недостающее — маппинг по slug в `config/` или новое поле в модели (решить при реализации)
- [ ] При ошибке API блок не рендерится, страница не падает

### PW-066-D: «Мои комментарии» текущего пользователя (S, ~2 ч)

**Решение.** Новый эндпоинт `GET /api/users/me/comments` (`get_current_user`), переиспользует сервис
`GET /users/{user_id}/comments`. Страница — клиентская часть через `useAuth()` + React Query (кука httpOnly, SSR без
пользователя не знает, кто он), для гостя — предложение войти.

**Критерии:**

- [ ] `GET /api/users/me/comments` + тест (401 без авторизации, список своих — с авторизацией)
- [ ] `my-comments` использует его; `'user-1'` в коде не осталось
- [ ] Гость видит CTA «Войти», а не пустой список
- [ ] Ключ запроса в `lib/query-keys.ts`

### PW-066-B: Поиск по статьям (M, ~1 день)

**Что уже есть.** `GET /api/articles?search=` — `ILIKE` по `title` и `excerpt` (`services/articles/queries.py:48`).

**Решение, этап 1 (эта задача).** Модалка поиска (как `SettingsModal`): инпут с debounce 300 мс, `useQuery` на
`/api/articles?search=&limit=10`, результаты — заголовок + категория + дата, клавиатура (↑↓ Enter Esc), `Cmd/Ctrl+K`.
Пустое состояние, «ничего не найдено», загрузка.

**Этап 2 (отдельная задача, не здесь).** Полнотекстовый поиск PostgreSQL (`tsvector` с русской морфологией, GIN-индекс,
поиск по `content`), ранжирование. `ILIKE '%x%'` на тысячах статей не масштабируется, но на текущем объёме достаточен.

**Критерии:**

- [ ] Кнопка открывает модалку, `Cmd/Ctrl+K` тоже
- [ ] Результаты кликабельны → `/{slug}`
- [ ] Поиск минимум от 2 символов, debounce, отмена устаревших запросов (React Query делает сам по ключу)
- [ ] Доступность: фокус-ловушка, `aria-*`, Esc закрывает
- [ ] Светлая/тёмная тема через SCSS-переменные темы

### PW-066-A: Рассылка (L, 2–3 дня) — требует решения

**Сейчас в API нет отправки email вообще** (нет SMTP/провайдера). Поэтому «подписка» — это две разные задачи: хранить
подписчиков и отправлять письма.

**Решение, этап 1 (эта задача):**

1. Модель `NewsletterSubscriber` (`email` unique, `status: pending|confirmed|unsubscribed`, `confirm_token`,
   `unsubscribe_token`, `source`, `created_at`, `confirmed_at`) + миграция.
2. `POST /api/newsletter/subscribe` — идемпотентно (повторный email → тот же ответ, без утечки «уже подписан»),
   rate-limit по IP.
3. Double opt-in: письмо со ссылкой `GET /api/newsletter/confirm?token=`. Для писем — сервис `services/email.py` с
   провайдером через настройки (SMTP Яндекс 360 / Unisender / Mailgun — **выбор за владельцем**).
4. `GET /api/newsletter/unsubscribe?token=` (обязательно по 152-ФЗ и здравому смыслу).
5. Форма шлёт реальный запрос; текст тоста соответствует реальности.
6. Админка: список подписчиков (read-only) в разделе «Продвижение» — можно отдельной подзадачей.

**Этап 2 (не здесь):** сами рассылки — шаблоны, отправка по новым статьям, статистика.

**Если провайдер почты пока не выбран**, минимально честный вариант: сохранять подписчика со статусом `pending` без
письма и заменить текст тоста на «Спасибо! Мы сообщим о новых материалах». Главное — убрать неправду про письмо.

**Критерии:**

- [ ] Email сохраняется в БД, дубликаты не создаются
- [ ] Double opt-in работает end-to-end (или честный текст, если провайдера нет)
- [ ] Отписка по ссылке
- [ ] Согласие на обработку ПД у формы (чекбокс или текст со ссылкой на политику)
- [ ] Тесты API: subscribe / повтор / confirm / unsubscribe / невалидный токен
