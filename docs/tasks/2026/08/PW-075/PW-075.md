# PW-075: индикатор загрузки на страницах со скрытым до гидратации контентом

## Информация о задаче

- **ID**: PW-075
- **Статус**: TESTING
- **Создано**: 2026-08-03
- **Приоритет**: Normal 📋
- **Компонент**: ⚛️ Web
- **Теги**: #ux #loading #ssr #hydration #framer-motion

## Постановка задачи

### Описание

На главной странице между аппбаром и футером в течение нескольких секунд после открытия видно пустое полотно.

Причина — не ожидание данных. Разметка приходит с сервера целиком, но hero-секция и карточки статей обёрнуты в
framer-motion с `initial={{ opacity: 0 }}`, и этот инлайновый `opacity:0` попадает в SSR-HTML. Пока не догрузился и не
исполнился JS, контент физически присутствует в DOM, но невидим. Аппбар и футер не анимируются — поэтому видны они, а не
остальное. Проверено на dev-контуре: в отданном HTML присутствует `opacity:0;transform:translateY(20px)`.

Тот же дефект есть на страницах категорий и отдельной категории — там анимированы и заголовок, и карточки, то есть
пустует вся контентная область.

### Цель

Пока контент невидим, пользователь видит спиннер по центру экрана, а не пустоту.

### Критерии приемки

- [x] Общий компонент `Spinner` — кольцо трёх размеров (`sm` / `md` / `lg`), верхняя дуга брендовым `--color-primary`,
      корректная работа в светлой и тёмной темах
- [x] `PageSpinner` — фиксированный оверлей по центру вьюпорта, размонтируется после гидратации
- [x] Спиннер появляется с задержкой 0.5s чистым CSS: при быстрой гидратации оверлей успевает уйти и мелькания нет.
      Задержка реализована анимацией, а не таймером на JS — до исполнения бандла таймер не сработал бы
- [x] Затухание и появление разнесены по двум элементам: на одном свойстве `animation … forwards` и `transition`
      конфликтуют, снятие анимации сбрасывает `opacity` скачком
- [x] Оверлей не перехватывает клики (`pointer-events: none`) — аппбар и футер уже интерактивны
- [x] Под `prefers-reduced-motion` вращение отключено через `animation: none`; глобальное правило
      `animation-duration: 0.01s !important` из `utils/_animations.scss` иначе превращает кольцо в мельтешение
- [x] Подключено точечно: `AppHomePage`, `AppCategoriesPage`, `AppCategoryPage`

### Предложенное решение

1. `components/common/spinner/` — `Spinner` (примитив) + `PageSpinner` (оверсостояние страницы), плоские SCSS с BEM по
   образцу соседних компонентов в `common/`
2. Монтирование в трёх клиентских компонентах страниц, у которых до гидратации пустует вся контентная область

### Почему не в root layout

Глобальный оверлей перекрывал бы читаемый текст там, где контент виден сразу. `ArticlePage` не использует framer-motion
— тело статьи отображается с первого кадра. На странице автора анимированы только заголовок и сетка статей, а биография
и контакты видны сразу, поэтому спиннер там был бы шумом.

### Проверки

- [x] `tsc --noEmit` — чисто; `eslint` — 0 ошибок (25 предупреждений — доэтапные, в изменённых файлах их нет)
- [x] SSR-HTML: главная, `/categories`, страница категории содержат `class="page-spinner"`; страница статьи — нет
- [x] После гидратации `document.querySelector('.page-spinner')` возвращает `null`
- [x] Вычисленные стили: `position: fixed`, центр спиннера в (640, 360) при вьюпорте 1280×720, `z-index: 1030`,
      `pointer-events: none`; цвет дуги `#7ac27a` в светлой теме и `#69b969` в тёмной

Скриншот не снят: панель браузера не отображалась, страница не композитила кадры — в такой вкладке заморожен и сам
framer-motion. Проверка выполнена по DOM и вычисленным стилям.

### Не входит в задачу

- Спиннер в `LoadMoreButton` — та же проблема с `prefers-reduced-motion`, теперь есть общий `Spinner` для замены
- Пересмотр самих анимаций появления (задержка `BASE_DELAY = 0.5` в `ArticleList`)
- Загрузочные состояния маршрутов (`loading.tsx`) — отдельный сценарий, ожидание данных, а не гидратации
