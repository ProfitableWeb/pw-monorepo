# ADR-004: Автопубликация запланированных статей

**Дата**: 2026-09-25

## Статус

Принято

## Контекст

Статью можно запланировать из админки (`POST /api/admin/articles/{id}/schedule`) и через MCP (`schedule_article`):
статус становится `scheduled`, в `published_at` пишется время в будущем. Публичные запросы, sitemap и RSS показывают
только `status = published`.

До этого решения механизма, который переводил бы `scheduled → published`, не было: запланированные статьи никогда не
выходили, хотя MCP-ресурс обещал «опубликуется автоматически».

Ограничения:

- API работает в одном Docker-контейнере (uvicorn), число воркеров может вырасти.
- Инфраструктура минимальна: без очередей, без Redis-воркеров, без отдельного cron-контейнера.
- Точность до минуты достаточна.

## Решение

Фоновая asyncio-задача в `lifespan` FastAPI раз в 60 секунд вызывает `publish_due_articles()`
(`src/services/articles/scheduling.py`):

1. Выбирает статьи `status = scheduled AND published_at <= now()`.
2. Для каждой выполняет **условный** `UPDATE ... SET status = 'published' WHERE id = :id AND status = 'scheduled'`.
3. Если `rowcount == 1` — статью опубликовал именно этот процесс: пишет audit log (`article.auto_publish`) и
   structlog-событие `article_auto_published`.

### Детали реализации

- Перед публикацией — та же проверка `_validate_publishable`, что при ручной публикации (title, content, excerpt,
  категория). Не прошедшая статья **не публикуется**, а возвращается в `draft` с записью `article.auto_publish_rejected`
  (и причиной) в аудит и warning в лог — иначе она висела бы в `scheduled` и повторяла ошибку каждую минуту.
- Условный `UPDATE` делает задачу безопасной при нескольких воркерах/репликах: статью публикует и логирует ровно один.
- Синхронный SQLAlchemy (ADR-001) вызывается через `asyncio.to_thread`, event loop не блокируется.
- Ошибка тика (например, БД недоступна) логируется как `article_auto_publish_failed`, цикл продолжается.
- Первый тик — сразу при старте: статьи, «проспавшие» простой API, публикуются немедленно.
- Флаг `ARTICLE_PUBLISHER_ENABLED` (по умолчанию `true`); в тестах выключен, сервис тестируется напрямую.
- `published_at` уже хранит нужное время, дополнительные поля не нужны.

### Видимость на сайте

Страницы web (`/`, `/[slug]`, `/categories`) — `force-dynamic`, статья видна сразу после тика. `sitemap.xml` и
`feed.xml` кешируются на 1 час (`revalidate = 3600`) — задержка до часа в них допустима. Если потребуется мгновенность —
on-demand revalidation из API (отдельная задача).

## Альтернативы

| Альтернатива                                                               | Плюсы                            | Минусы                                                                                  | Почему отклонена                                   |
| -------------------------------------------------------------------------- | -------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------- |
| «Ленивая» публикация: `published OR (scheduled AND published_at <= now())` | Нет фоновых процессов            | Условие надо продублировать во всех запросах, счётчиках, sitemap, RSS; статус в БД врёт | Легко забыть одно место — тихие баги               |
| Внешний cron → `POST /api/admin/system/publish-due`                        | Явно, не зависит от процесса API | Ещё одна движущаяся часть в деплое и секрет для вызова                                  | Избыточно для текущего масштаба                    |
| APScheduler / Celery beat                                                  | Гибкое расписание                | Новая зависимость (Celery — ещё и брокер) ради одной задачи раз в минуту                | Избыточно; можно вернуться при росте фоновых задач |

## Последствия

### Положительные

- Запланированные статьи выходят в срок без участия человека.
- Статус в БД отражает реальность; все запросы остаются простыми (`status = published`).
- Каждая автопубликация видна в аудит-логе.

### Отрицательные

- Точность — до интервала тика (≤ 60 с).
- При нескольких воркерах каждый делает свой SELECT раз в минуту (нагрузка ничтожна).

### Риски

- Если API не запущен, публикации ждут его старта (первый тик сразу при старте их догонит).
- Изменение статуса вручную между SELECT и UPDATE обрабатывается условным UPDATE — статья не будет перезаписана.
