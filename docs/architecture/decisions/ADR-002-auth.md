# ADR-002: Аутентификация

**Дата**: 2026-02-12

## Статус

Принято; изменено 2026-08-02 — Google исключён из состава OAuth-провайдеров (см. «Изменения» в конце документа).

## Контекст

Нужна система аутентификации для админ-панели и комментариев на блоге. Требования: OAuth через популярные российские и
международные провайдеры, ролевой доступ, безопасное хранение токенов.

## Решение

JWT в httpOnly cookies с OAuth через Yandex, Google и Telegram.

### Детали реализации

**Токены**:

- `access_token`: 15 минут, httpOnly cookie
- `refresh_token`: 7 дней, httpOnly cookie
- Автоматическая ротация refresh-токена при обновлении

**Почему cookies, а не localStorage**:

- Защита от XSS-атак (JS не может прочитать httpOnly cookie)
- Автоматическая отправка с каждым запросом (не нужен interceptor)
- CSRF защищён через SameSite=Lax

**OAuth-провайдеры**: Yandex, Telegram (Google исключён 2026-08-02, см. «Изменения»)

**Роли**:

| Роль     | Доступ                                            |
| -------- | ------------------------------------------------- |
| `admin`  | Полный доступ, управление пользователями          |
| `editor` | Редактирование всех статей                        |
| `author` | Создание и редактирование своих статей            |
| `viewer` | Комментирование (OAuth-пользователи по умолчанию) |

**Защита админ-панели**: middleware проверяет роль `admin` или `editor`, иначе редирект на `/login`.

## Альтернативы

| Альтернатива       | Плюсы              | Минусы                                              | Почему отклонена    |
| ------------------ | ------------------ | --------------------------------------------------- | ------------------- |
| JWT в localStorage | Простая реализация | Уязвим к XSS                                        | Безопасность важнее |
| Session-based auth | Простота           | Stateful, проблемы с масштабированием               | JWT гибче           |
| NextAuth.js        | Готовое решение    | Привязка к Next.js, не подходит для FastAPI backend | Бэкенд на Python    |

## Последствия

### Положительные

- Безопасное хранение токенов (httpOnly)
- Единая авторизация для web и admin через один API
- Гибкие роли для будущего расширения

### Отрицательные

- Сложнее отладка (токены не видны в DevTools)
- Нужна регистрация приложения у каждого OAuth-провайдера

## Изменения

### 2026-08-02 — Google исключён из состава провайдеров входа

**Решение:** состав провайдеров входа ограничивается российскими информационными системами.

Контекст. Ч. 10 ст. 8 ФЗ-149 (в ред. ФЗ от 31.07.2023 № 406-ФЗ и ФЗ от 12.12.2023 № 588-ФЗ) устанавливает для
российского владельца сайта перечень допустимых способов авторизации: абонентский номер российского оператора, ЕСИА, ЕБС
либо иная информационная система, владелец которой — гражданин РФ или контролируемое Россией юрлицо.

Применимость нормы к ProfitableWeb однозначно не установлена: обязанность сформулирована для случая, когда доступ к
информации предоставляется только зарегистрированным пользователям, тогда как здесь весь контент открыт, а регистрация
нужна лишь для комментирования. Решение принято не по факту установленного несоответствия, а как выбор в пользу
однозначно безопасной конфигурации: сохранять зависимость от иностранного провайдера ради одной кнопки входа смысла нет,
а стоимость отказа минимальна.

Удалены: модуль `src/auth/oauth/google.py`, ветки провайдера в `api/auth.py`, настройки `google_client_id` /
`google_client_secret`, кнопки входа в web и admin, переменные `GOOGLE_CLIENT_*` из окружения и CI.

Значение `google` в колонках `users.oauth_provider` и `user_oauth_links.provider` **сохранено** — это свободная строка
(`String(50)`, не enum), миграция не требуется. Пользователи, ранее вошедшие через Google, сохраняют доступ к аккаунту
через пароль (форма «Установить пароль» в настройках профиля), Яндекс ID или Telegram; существующую привязку Google
можно отвязать в настройках, подключить заново — нельзя.

**Новых иностранных провайдеров входа не добавлять.**
